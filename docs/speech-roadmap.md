# Sonemory 设备端语音识别评估与路线

版本：1.0（2026-08-15）

## 结论

Sonemory 的主要问题不是“有没有语音识别”，而是儿童短词、非母语发音、家庭噪声与浏览器差异叠加后，识别器容易把设备问题误判成知识错误。路线应同时优化四层：音频输入、识别引擎、限定词表判定、真实儿童语音评测。

当前最合适的策略是：

1. 先使用浏览器原生设备端 Web Speech，保持零第三方运行依赖和最低接入成本；
2. 用真实目标词表和儿童样本建立可重复基准；
3. 如果跨设备差异仍不可接受，再开发 sherpa-onnx 流式 WASM 原型；
4. Whisper/WebGPU 和原生应用作为设备能力更强或多语种长语音场景的补充；
5. 云端识别只能作为家长明确选择的回退，不能默认上传儿童声音。

“本地”主要提升隐私、断网能力和延迟可控性，并不自动等于准确率更高。准确率必须用 Sonemory 自己的儿童短词场景测量。

## 已在 v0.2–v0.4 实现

- 检测浏览器是否支持 `SpeechRecognition.available()` 与 `install()`；
- 按语言检查、下载设备端语音包；
- 提供“设备端优先并自动回退”“仅设备端”“浏览器默认服务”三种模式；
- 本地语言包可用时设置 `processLocally = true`；
- 保留最多五个候选结果，而不是只判断第一候选；
- 向支持上下文偏置的识别器提供当前目标词、别名及常用英语指令；
- 低置信度或连续未识别仍计为“未听清”，不计为知识错误；
- 把识别等待上限从 11 秒缩短为 10 秒，暂停仍会立即中断识别。
- 提供可分别启用的 AI / 自托管 TTS 与 STT 网关，不把任何云平台 SDK 或长期密钥写入浏览器；
- AI STT 录音请求回声消除、降噪和自动增益，并使用轻量 VAD 提前结束单词录音；
- AI STT 会传入当前目标词、别名和指令，便于网关映射为平台热词或提示；
- 只有家长明确确认数据边界后才允许把孩子作答音频发送到外部网关。

具体协议、平台比较与验收标准见 [AI 语音接入与选型](ai-speech-integration.md)。

Chrome 139 开始提供设备端 Web Speech 能力，可查询语言支持、安装所需资源，并选择本地或默认处理；Web Speech 规范中的 `processLocally`、`available()` 和 `install()` 仍属于正在演进的浏览器能力，因此必须保留功能检测和回退。[Chrome 139 发布说明](https://developer.chrome.com/release-notes/139)、[Web Speech API 规范](https://w3c.github.io/speech-api/speechapi.html)、[设备端能力说明](https://github.com/WebAudio/web-speech-api/blob/main/explainers/on-device-speech-recognition.md)

## 后续方案优先级

| 优先级 | 方案 | 适合 Sonemory 的原因 | 主要代价与风险 |
|---|---|---|---|
| 1 | 原生设备端 Web Speech 持续优化 | 无新增包、安装简单、可以离线、现有接口改动小 | 浏览器/系统覆盖不一致；模型不可控；儿童英语短词准确率未知 |
| 2 | sherpa-onnx 流式 Zipformer + WASM | 真正本地、流式低延迟、支持英语及中英模型、引擎可控 | 官方双语 WASM 示例资源约 199 MB 数据加约 10 MB WASM；首次下载和低端设备内存压力明显；模型许可需逐个核对 |
| 3 | whisper.cpp 量化模型 + WASM/WebGPU | 多语种强、生态成熟、可完整离线 | 官方浏览器示例的量化 tiny.en 约 31 MB、base.en 约 57 MB，但页面明确建议快速桌面设备；Whisper 对单个孤立短词未必优于流式限定词表模型 |
| 4 | Transformers.js + Whisper/WebGPU | 前端集成方便，可使用 WASM 或 WebGPU、量化模型选择多 | WebGPU 覆盖和驱动差异；模型下载、显存、预热时间及包依赖增加；必须移入 Worker 避免阻塞界面 |
| 5 | 原生 App/桌面伴侣进程 | 可控制麦克风、线程、SIMD、NNAPI/Core ML/DirectML，跨会话缓存模型 | 安装和维护成本最高，PWA 的零安装优势下降；本地网络调用还涉及浏览器权限与安全边界 |
| 6 | 可选择的云端回退 | 在弱设备或本地模型不支持的语种上可能更准确 | 儿童隐私、家长同意、网络延迟、成本、数据保留和跨境合规；不应成为默认路径 |

参考实现显示 sherpa-onnx 可通过 WebAssembly 在浏览器中做实时识别，并提供英语、中英和多语模型示例；其官方构建示例也清楚展示了模型体积成本。[sherpa-onnx WASM 文档](https://k2-fsa.github.io/sherpa/onnx/wasm/index.html)、[WASM 构建示例](https://k2-fsa.github.io/sherpa/onnx/wasm/build.html)

whisper.cpp 官方提供实时浏览器 WASM 示例和量化模型；Transformers.js 官方也展示了用 WebGPU 运行 Whisper ASR，但同时指出 WebGPU 支持仍不是所有设备都有。[whisper.cpp stream.wasm](https://github.com/ggml-org/whisper.cpp/tree/master/examples/stream.wasm)、[Transformers.js WebGPU](https://huggingface.co/docs/transformers.js/guides/webgpu)

## 不更换模型也能继续提升的环节

### 音频输入

- 首次使用增加 3 秒环境音与正常说话音量校准；提示“太轻、太远、背景持续噪声”；
- 在可控音频管线中启用并实测 `echoCancellation`、`noiseSuppression` 和 `autoGainControl`，不要假设所有设备默认效果一致；
- 使用 VAD 识别说话起止，减少把提示音尾部、键盘声或长静音送进模型；
- 播报结束后留 200–400ms 防回声窗口，再开启识别；耳机和外放应分别测试；
- 记录设备类型、输入电平、等待耗时和错误类型，不默认保存原始音频。

### 限定词表判定

- Sonemory 每次只期待一个目标词或少量指令，应把开放听写转换成“候选生成 + 限定词表判定”；
- 对目标词、展开后的 `sth/sb`、别名和指令使用识别器支持的 contextual bias；
- 将音素距离、拼写距离与识别置信度组合为“正确 / 明确错误 / 不确定”，不确定应重听而不是判错；
- 短词、同音词和最小对立词必须设置更严格阈值，不能为了提高通过率而产生大量误判；
- 跟读阶段只验证“确实检测到人声”与大致目标匹配，不把通用 ASR 当作专业发音评分。

### 交互效率

- 预加载下一题所需模型状态和上下文词表；模型只初始化一次并放入 Worker；
- 设备端模型和语种包显示下载体积、进度、占用和清除入口；
- 将初始化时间、首个结果时间、最终结果时间分开测量；
- 连续两次未听清后允许孩子通过网页按钮或学习设置继续，不能陷入语音死循环。

## 必须建立的准确率基准

评测集应来自获得监护人同意的目标年龄段，覆盖安静房间、电视背景声、远场、不同口音、低声说话和常见设备。若不能合法保留录音，可在一次性测试后只留不可回溯的汇总指标。

每个引擎至少报告：

- 目标词正确接受率；
- 错词错误接受率（这是教学产品最危险的指标）；
- 正确答案被拒绝率；
- 未识别率和两次重试率；
- 指令识别率；
- 首次可用延迟、热启动 P50/P95 延迟、耗电和峰值内存；
- 按年龄、设备、噪声、词长、短语/单词和口音拆分的结果。

在形成这套基准以前，不应宣传“本地识别更准确”或“可以评估发音”。

## 下一轮建议

下一轮先做一个不进入正式包的 sherpa-onnx 英语流式原型，用同一批 50–100 个目标词和至少 5 类设备，对比浏览器设备端 Web Speech。只有当错误接受率、正确拒绝率或 P95 延迟出现有意义改善，并且模型体积在家庭网络可接受范围内，才将其纳入正式离线包。
