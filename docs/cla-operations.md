# CLA 执行与留档流程

CLA 的价值取决于能否证明“谁、在什么身份下、对哪个版本的协议、何时作出接受”。仅在 CONTRIBUTING 中写一句“提交即同意”不够稳妥。

## 个人贡献者

1. Pull Request 必须使用仓库模板。
2. 贡献者勾选个人身份，并勾选 CLA 明示接受项。
3. 维护者核对 GitHub 账号、提交作者与声明是否一致。
4. 如提交可能属于雇主、学校或客户，应暂停合并并要求权利证明或组织 CLA。
5. 合并后在 [CLA-ACCEPTANCE.md](../CLA-ACCEPTANCE.md) 记录公开 GitHub 账号、CLA 版本、首个接受 PR、日期与贡献身份。

## 组织贡献者

1. 使用 [组织 CLA 模板](legal/ENTITY-CLA-TEMPLATE.md)，填完整法律主体、关联公司、授权贡献者、适用法律和签字信息。
2. 由组织及项目所有者的有权代表签署。
3. 完整合同可私密保存；公开记录只保留组织名称、协议版本、签署日期、覆盖账号和内部文档编号，避免公开地址与签名。
4. 每个 PR 仍需声明代表哪个已登记组织提交。
5. 授权人员离职或权限终止后更新记录；终止不影响此前已提交贡献的许可。

## 版本管理

- 对 CLA 的实质变更必须增加版本号和生效日期。
- 旧版已授权权利不因新版本发布而消失。
- 是否要求既有贡献者重新接受新版，取决于变更内容；扩大项目权利时应重新取得明确同意。
- 保留每个历史版本，不能用覆盖文件的方式抹去已接受文本。
- 建议在正式接收外部贡献后，把协议版本归档到 `docs/legal/archive/`。

## 合并控制

合并前必须同时满足：

- [ ] PR 中有明确 CLA 接受记录。
- [ ] 贡献身份为个人，或组织 CLA 已登记。
- [ ] 贡献者有权提供代码、文档、音频、数据和其他素材。
- [ ] 第三方内容已列出来源与许可证。
- [ ] 不包含教材、密钥、保密信息或可识别儿童数据。
- [ ] CLA 记录已更新或确认已有覆盖记录。

未来可以引入 CLA Assistant 等自动化服务，但自动化只能帮助记录，不能修复协议主体、授权范围或签署权限本身的问题。
