# Sonemory 许可策略与影响评估

版本：1.1（2026-08-15）

> 本文记录项目在首次公开发布阶段形成的许可决策、适用边界与执行要求，方便维护者、贡献者和商业合作方得到一致答案。它是决策与操作说明，不替代针对具体交易或司法辖区的法律意见。

## 一、最终决策

Sonemory 采用以下三层结构：

1. **社区代码：`AGPL-3.0-only`**  
   任何人均可在遵守 AGPL 的前提下使用、修改、部署、分发或收费。选择 `-only`，表示使用者不能自动改用未来版本的 AGPL。
2. **闭源商业路径：单独书面授权**  
   不希望或无法履行 AGPL 条件的组织，需要与项目所有者签署商业许可。公开仓库中的“商业授权说明”本身不授予任何例外。
3. **外部贡献：CLA**  
   个人贡献者保留版权，但授予项目所有者永久、不可撤销、可转让和可再许可的版权及必要专利权。组织贡献需要另行签署组织版 CLA。

代码许可与品牌、教材、音频、模型、用户数据相互独立，不能互相替代。

## 二、为什么放弃 Apache-2.0

Apache-2.0 对采用、集成和闭源商业化非常友好，但第三方可以在保留通知的前提下形成闭源产品或服务，项目所有者较难用代码许可推动改进回流或形成商业授权谈判空间。

AGPL 增加了强互惠要求，尤其覆盖“修改后通过网络提供给用户”的场景，更符合 Sonemory 未来可能作为网页、家庭服务、学校平台或云端语音服务运行的形态。代价是部分企业、硬件厂商和开源贡献者会因合规成本而降低采用意愿。

因此，AGPL 不是单纯“更严格”，而是用较低的闭源采用率换取：

- 修改版源码回流的机会；
- 更清晰的闭源商业授权入口；
- 对直接复制并封闭运营行为更强的谈判筹码。

## 三、常见场景判断

| 场景 | 默认路径 | 主要影响 |
|---|---|---|
| 家庭或个人直接使用公开版本 | AGPL | 可免费使用；不因录入自己的词表而改变词表版权。 |
| 学校或企业使用未修改版本 | AGPL | 商业或组织内部使用本身不收费；分发副本时仍需履行许可证与源码义务。 |
| 修改后通过网络向学生或客户提供服务 | AGPL | 应向实际远程交互用户显著提供该运行版本的完整对应源码。 |
| 把 Sonemory 打包成 App、固件或设备并交付 | AGPL 或商业授权 | AGPL 路径通常需要同时提供许可证、对应源码及适用的安装信息；不适合时应谈商业授权。 |
| 与专有系统形成一个不可分割的组合产品 | 优先商业授权评估 | 是否构成一个作品依赖具体集成方式，不能仅凭“API”“进程分离”或“容器分离”下结论。 |
| 与专有系统保持独立、仅按通用协议协作 | 个案评估 | 可能属于独立聚合，但仍需审查通信方式、打包方式和用户体验。 |
| 只进行私有修改，既不分发也不让他人远程交互 | 通常无公开义务 | 一旦向外分发或提供网络交互，需要重新评估。 |
| 遵守 AGPL 的收费服务或商业发行 | AGPL | 允许收费；“商业”不等于必须购买商业许可。 |
| 不愿公开修改版源码的闭源产品或服务 | 商业授权 | 必须在使用前取得签署的书面许可。 |

## 四、AGPL 的核心影响

### 1. 网络源码义务只针对修改版

AGPL 第 13 条的额外网络义务针对支持网络交互的**修改版**。部署者应通过标准、便捷且免费的方式，向远程交互用户提供该运行版本的 Corresponding Source。

“对应源码”不是只放原始 Sonemory 仓库链接，而是应能对应实际运行版本，并包括生成、安装、运行和修改该版本所需的代码与脚本，以及许可证要求纳入的相关组件。

### 2. 分发仍然受 GPLv3 主体规则约束

网页下载、PWA、桌面封装、移动 App、设备固件或离线安装包都可能构成向用户提供副本。应保留许可证与版权声明，并保证源码与交付版本匹配。

### 3. 已公开版本的 AGPL 权利不可追回

项目所有者可以停止发布新版本或对未来版本更改策略，但已经合法取得某一 AGPL 版本的用户仍可继续依照该许可证使用和再分发该版本。商业价值应建立在新版本、品牌、托管、支持、数据服务和完整版权链上，而不是假设可以撤回旧版本。

### 4. `AGPL-3.0-only` 的兼容性代价

`-only` 保留了项目对未来许可证版本的决策权，但比 `-or-later` 更容易遇到未来许可证兼容问题。引入依赖前必须逐项核对，不能仅凭“也是开源协议”判断兼容。

## 五、商业授权的边界

商业授权不是公开仓库中的第二份自动许可证，而是特定客户与项目所有者签署的合同。合同至少要确定：

- 签约主体及其关联公司；
- 获准使用的版本、提交或产品线；
- 部署数量、设备数量、用户范围或 SaaS 范围；
- 是否允许修改、再分发、转授权和委外开发；
- 费用、期限、续费和审计机制；
- 源码交付、升级、维护和支持范围；
- 保证、赔偿、责任限制和终止后处理；
- 数据保护、儿童隐私、安全和出口管制责任；
- 是否另行授予商标、Logo、域名或“官方版本”称谓。

商业许可只能覆盖项目所有者实际拥有或已取得再许可权的代码。第三方库、模型、音色、字体、数据集与教材内容必须继续遵守各自许可，不能由 Sonemory 商业合同单方面改写。

## 六、CLA 对商业化的作用

如果没有 CLA，外部贡献者通常只按公开 AGPL 提供其代码；项目所有者未必能把这些贡献放入专有商业版本。GNU 的许可 FAQ 也明确指出，重新许可包含他人贡献的版本需要取得贡献者许可。

Sonemory 选择“贡献者保留版权 + 宽授权 CLA”，而不是版权转让：

- 贡献者仍可在其他项目中使用自己的代码；
- 项目所有者获得 AGPL 发布、商业再许可和项目继承所需权利；
- 公开社区版中采用的贡献继续在 AGPL 下提供；
- 个人与组织贡献分别留存可核验的接受记录。

周边代价是 CLA 会增加贡献摩擦，并可能引发“社区贡献被用于闭源版本”的顾虑。缓解方式是保持条款简短透明、明确贡献者保留版权、承诺公开社区版仍提供被采用贡献，并公开记录 CLA 版本与接受证据。

## 七、内容、模型与数据不随代码许可

Sonemory 的“教材由用户导入”原则同时是产品原则和许可风险隔离措施：

- 官方教材、教辅、付费课程、词表及录音不因导入软件而变成 AGPL 内容；
- 仓库不得收录无权再分发的教材派生内容；
- 演示数据需要原创、公有领域或有明确兼容许可；
- 未来引入 ASR/TTS 模型时，要分别审查代码许可、模型权重许可、训练数据限制、声音/人格权、地域与商业使用限制；
- “可研究使用”“非商业使用”“仅限某平台”不等同于可进入 AGPL 社区发行或商业版本。

儿童隐私、家长同意、录音处理和数据跨境属于隐私与产品合规问题，不由开源许可证解决。

## 八、许可证不能替代创意、专利与商业秘密保护

著作权和 AGPL 保护的是 Sonemory 已经形成的代码、文档、界面素材等具体表达，不保护抽象的“通过音频提升记忆效率”想法、教学思想、方法或系统概念。第三方如果没有复制受保护表达，而是独立实现同类创意，通常不是开源许可证能够阻止的对象。

因此，需要按对象组合保护：

- **代码与文档**：用著作权登记证据、提交历史、版本标签、版权声明、AGPL 和 CLA 形成权利链；
- **名称与来源识别**：用 Sonemory 文字商标、Logo、音频标识、域名和应用商店名称管理降低混淆；商标保护通常依赖目标国家或地区的申请、注册与持续使用；
- **真正具有技术创造性的方案**：在公开前由专利律师判断是否值得申请、在哪里申请以及公开时点；本仓库的文档不能替代专利检索或可专利性意见；
- **不准备公开的商业信息**：算法调参经验、供应商条件、客户清单、定价和未发布路线可用访问控制、保密协议和最小知情范围保护。

公开源码与商业秘密存在天然张力：任何为了安装、运行或修改 AGPL 版本而属于 Corresponding Source 的材料，都不应一边作为商业秘密保留，一边又依赖公开 AGPL 分发。可以把独立开发的托管、内容服务或商业运营能力另行设计，但“独立进程”“API”“插件”或“容器”只是技术事实，不会自动得出独立作品的法律结论；模块边界应在形成产品架构和合同前个案审查。

## 九、品牌与商标影响

AGPL 授予的是著作权层面的软件权利，不自动授予 Sonemory 名称、Logo、音频标识、宣传语或“官方版本”身份。衍生版本应使用自己的品牌，只能为准确说明来源而合理提及 Sonemory。

未来商业授权如要包含白标、联合品牌或官方认证，必须在合同中单独、明确授权。建议在主要市场尽早完成名称检索、域名与应用商店账号占位，并在投入大规模推广前咨询商标代理人。

## 十、对社区和产品路线的影响

### 正面影响

- 阻止修改版长期以闭源网络服务形式吸收社区成果；
- 为学校平台、硬件厂商和闭源 SaaS 建立明确商业入口；
- CLA 使未来融资、并购、项目主体迁移和商业再许可更可执行；
- 商标分离降低非官方衍生版本造成品牌混淆的风险。

### 负面影响

- 部分企业安全或采购政策会直接排除 AGPL；
- 与专有 SDK、模型或应用商店条款组合时需要更多审查；
- CLA 会降低零门槛贡献率；
- 维护者需要长期保存版本源码、第三方通知、CLA 证据和商业合同范围；
- 如果核心功能以后大量依赖无法商业再许可的第三方代码，双许可模式会失去实际价值。

## 十一、每次发布前的执行清单

- [ ] `LICENSE` 保持未经修改的 AGPL v3 全文。
- [ ] 包元数据和源码 SPDX 标识均为 `AGPL-3.0-only`。
- [ ] 产品界面提供当前发布版本对应的源码与许可证入口。
- [ ] 创建不可变版本标签，源码入口与实际部署版本一致。
- [ ] 生成并检查第三方组件、模型、素材与数据许可台账。
- [ ] 外部 PR 已完成个人 CLA，或组织 CLA 已由有权代表签署。
- [ ] CLA 接受记录可核验，且使用正确协议版本。
- [ ] 商业版本只包含项目所有者有权商业再许可的组成部分。
- [ ] 商标授权、支持、保证和隐私义务没有被含糊地混入代码许可。
- [ ] 对外文案没有把“商业使用”错误描述为一律付费。
- [ ] 计划公开的技术方案已完成必要的专利/商业秘密评估，没有因仓促披露破坏既定知识产权策略。

## 十二、尚需项目所有者决定的事项

在接受首位外部贡献或签署首份商业合同前，必须补齐：

1. 项目所有者/签约方的真实个人姓名或公司全称；
2. 通知邮箱和法律文书送达地址；
3. 商业合同适用法律、争议解决地和责任上限；
4. CLA 的电子签署与记录保存流程；
5. 商标申请主体以及商业许可是否默认包含任何品牌权利。
